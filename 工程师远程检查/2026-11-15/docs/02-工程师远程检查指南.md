## 2. 为什么不能克隆后直接启动

- 当前启动器会连接现有 Prefect、注册或核对部署、启动 worker 并处理控制 session，不是只读工具。
- 当前配置中的 Windows 绝对路径和 LAN 地址属于用户现场，换机器要重新映射。
- 实际 `.venv` 继承系统 site-packages；包版本快照已提供，但这不是完整跨平台安装锁文件。
- WPS/Office 转换、Nimble 和 WSL 离线计数器依赖现场软件及模型文件，这些没有随 Git 分发。
- 凭据使用现场私有配置/环境变量，部分 Windows 凭据受 DPAPI 保护；不能复制密文给另一台机器就认为可用。
- 文章库 Dockerfile 依赖现有 Qdrant 基础镜像、已构建前端和历史导入文件；业务历史记录及构建产物未随源码上传。
- 前端存在指向旧工程 `node_modules` 的本机 alias，必须核对 package/lock 与构建配置。

隔离复现时请使用临时目录、假的请求/响应、临时 NAS 目录和独立测试数据库。复制样例配置后先改成本地隔离目标，再决定是否加载对应模块。

## 3. 本次提供的最小离线验证

仓库内 `tools/run_offline_checks.py` 只运行三组既有测试，覆盖模型未知结果不重发、交付回执复用及精确工作区边界。它禁用测试 conftest 自动绑定、阻断 socket 连接，并用临时路径替代导入时所需的两个现场路径常量。

```powershell
python tools/run_offline_checks.py
```

此命令需要 Python 与 pytest 及相关导入依赖。本次在现场现有 Python 3.14 / pytest 9 环境中运行，16 项通过，网络连接尝试为 0。这不等于完整环境复现、全量测试或真实论文链验收。

其他测试包含 Prefect test harness、临时服务、文件删除 fixture 和 PostgreSQL schema 操作；不要把生产 DSN 或现场 NAS 根配置进测试。不要直接运行整个仓库的 pytest：历史候选中有重复测试名、机器路径和不完整实验片段。

## 5. 需要现场配合时如何取证

仅靠 GitHub 可以检查源码、隔离测试和提交修复建议。真实模型、现场账户、NAS 原文、服务器状态和故障请求需要用户现场另行提供最小脱敏证据或授权连接。此次上传不包含远程登录会话、SSH 私钥、路由管理令牌或 1Panel 登录入口。

建议按具体问题索取字段而不是完整目录，例如原 request/attempt 身份、状态时间、错误类别、请求/响应摘要、原目标状态和证据缺口。完整论文、原始回答和秘密配置留在用户控制的私有环境。

修复建议可以通过 Git 分支或补丁交回。生产启停、改共享路由、重试 unknown、重新入库、写 NAS、删除原件和删除工单，应分别说明影响并按用户安排执行。不要把历史运维脚本当成默认安装命令。
