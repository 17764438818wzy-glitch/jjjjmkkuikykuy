# 通用 RAGFlow 上传与解析工作池设计

## 目的和适用范围

今后从论文预处理工作台发起的自动批量、流式批次和手动选择上传，都进入同一套任务队列。工作池负责把文件可靠地送到指定知识库、持续补满解析槽位、记录远端状态并在断线后安全恢复。教育链路是首个验证场景；财会及以后新增的专业链路沿用同一调度底座，各自保留现有的知识库、Pipeline、准入字段和 artifact 规则。RAGFlow 网页内直接拖拽的上传不经过工作台，无法由本地队列接管；统一调度的入口是工作台。

首轮目标是尽快完成可处理论文的交接。质量暂缓、剔除和技术失败分别记录并释放槽位，留待按原因复核；不会为了追求通过数把它们改成“入库”。Agent 最终学习的范例仍需具备稳定来源、可定位正文和专业 Pipeline 的准入结果。旧论文的数据和结论不能迁移到新研究对象。

## 现有入口与扩容依据

| 入口 | 当前行为 | 接入通用池时保留的约定 |
| --- | --- | --- |
| 自动按专业交接 `auto_ragflow.handoff` | 按专业映射 md／图片库，可用线程池并行上传，再直接提交主文档解析 | 专业或批次指定的目标库、自动审批、知识包指纹和原有回执展示 |
| 工作台手动上传 `upload_routed_items` 及“导入选中项” | 用户选择已审核文件，按角色分流；两个界面动作分别存在仅上传和上传后解析的语义 | 用户明确选择的目标库、人工审核门槛、原按钮的解析意图和手动任务优先级 |
| 教育流式导入 `education_stream_ingest` | 另有一份 JSON 回执，最多三个正文请求在途，上传、轮询和收尾共用同步循环 | 稳定 `paper_id`、教育身份交接、教育库绑定和已上传远端文档 ID |

教育快速 Pipeline v5 已成功的 90 篇样本解析耗时中位数约 40 秒、90% 不超过约 56 秒。这不是端到端吞吐量，也未证实 RAGFlow 服务器实际执行并发。教育导入器的 `progress_msg` 会把部分暂缓／剔除显示为泛化排队文字；现有连续三次后的 120 秒等待属于错误退避。约 526 篇的教育回执文件已有约 654 KB，十万篇按同等记录量外推约 125 MB，多次整文件重写不适合长期队列。

## 方案决策

| 方案 | 评估 |
| --- | --- |
| 每条专业链路各写一套并行上传器 | 上线快，但重复实现去重、恢复、状态展示和并发控制，无法统一控制 RAGFlow／模型负载 |
| 一个通用调度内核，入口及专业规则用适配器接入 | **采用**。统一任务生命周期，教育先验证，随后将自动和手动入口逐步切换；专业语义仍留在各自 Pipeline |
| 立即启动多个进程共同操作现有 JSON 回执 | 外部写入与本地状态可能竞争，无法可靠防重；不采用 |

当前活跃教育批次先保留原有单写入者和回执，修正误退避及补位顺序。新通用队列用本地 SQLite WAL 保存任务与尝试记录，供后续批次和逐步迁入的入口使用。需要跨主机分布式执行时再改用支持跨主机事务的数据库，不共享网络目录中的 SQLite 文件。

## 通用内核与专业适配器

入口只负责验证来源、选择目标并提交任务；网络写入统一由工作池执行。逻辑导入请求记录批次、手动／自动来源、逻辑来源 ID、文件及知识包哈希、目标服务和路由版本。每个实际上传对象成为一个 artifact 任务：目标知识库 ID、角色、内容哈希、远端文件名、需要解析与否及所需 Pipeline ID。正文解析有独立的阶段状态及尝试历史，并保存远端文档 ID 和提交意图；数据库可用关联表或同一任务行的独立阶段字段实现，不要求每个概念单独建表。

自动预处理每完成并持久保存一篇已批准论文，就可将它入队；批次结束时再做一次幂等清扫。手动选择的任务直接入队。入队确认表示“已排队”，只有远端回执核实后才显示“已上传”。

全局去重键包含规范化的服务地址、目标知识库 ID、逻辑来源 ID 和 artifact 角色。同一来源的内容哈希改变时进入版本冲突／受控替换流程，不能静默覆盖旧远端文档；同一来源按明确路由进入不同知识库则各有独立回执。逻辑来源 ID 优先使用稳定 `paper_id`，旧包可由经过核验的源文件哈希或内容指纹补齐；缺乏可靠身份的任务停在预检，不用文件名冒充身份。数据库和日志不保存 API 密钥或服务器密码。

今后新上传的远端文件名要在 255 字节限制内包含稳定来源 ID 与内容哈希片段；若专业 Pipeline 仍校验原预处理任务编号，也须保留该编号。文件名只是远端定位线索，不能独自证明远端文件字节与哈希一致。已知远端 ID 的文档按 ID 核对；若上传确认丢失，必须有远端内容哈希或可下载字节核验才自动认领，无法核验则停在“不确定”，不凭同名文档重传或认领。解析提交确认丢失时，`UNSTART` 也不能证明提交未发生。

同一份已核验内容先由“只上传”入口提交、后由“导入并解析”入口提交时，复用原上传任务和远端文档，并追加解析意图；不重新上传。后来的“只上传”请求也不能取消已经明确提交的解析。各入口按自己请求的阶段展示完成状态。

任务可能在队列中等待较久。执行上传前须重新核对待上传文件的内容哈希和知识包预检状态；文件消失或发生变化时停止该任务并留下来源异常，不能按旧回执上传新内容。

专业适配器仅定义以下规则，不接管通用队列：

1. **预检和路由**：自动任务沿用专业／批次目标库映射；手动任务沿用用户明确选择的目标库。身份、哈希、隐私和审核门槛仍按该入口及知识包规则校验。
2. **解析策略**：哪些角色需要 RAGFlow parse、绑定哪个 Pipeline、何时启用辅助投影。工作台原有“只上传”和“导入并解析”操作各自保留，任务显式记录解析意图；论文主 `ingest.md` 可进入专业论文 Pipeline，原图保留定位材料角色，不进入主文档论文解析。
3. **结果解释**：将专业 Pipeline 的输出归为准入、质量暂缓、质量剔除、技术待核查或远端不确定，并保留原始裁决字段。进度文字不能单独证明质量原因。
4. **后处理钩子**：教育已准入论文构建确定性 Tree 和方法 Graph；财会继续使用其既有 Pipeline 与 Profile／Graph／Wiki 约定。通用工作池不预设某个专业的标注字段或四级分类。

## 队列状态与即时补位

```text
自动／手动／流式入口 → 预检 → 待上传 → 上传池 → 已上传 → 待解析 → 解析池
                                                       ├─ 准入 → 专业后处理池
                                                       ├─ 暂缓／剔除 → 二次复核清单
                                                       └─ 技术／不确定 → 安全核查清单
```

上传和解析分别记录 `intent`、`submitted`、远端 `running` 与终态。API POST 前先持久化意图；网络超时、进程重启或租约过期后，先按远端文档 ID、名称、知识库和 Pipeline 对账，再决定下一步。结果不确定时不自动重复上传或解析。若远端同一身份出现多个候选文档，停在人工核查；任务不会因为本地超时被当成未提交。

一个调度器拥有任务状态写入权，各 API 工作线程使用独立客户端，把结果交回调度器提交事务；入口只做幂等入队。正文上传、正文解析、图片材料和专业后处理分池；图片及 Tree／Graph 失败保留各自回执，不占正文解析槽。初始验证容量为上传 2、正文解析 3、图片 2、本地后处理 2；这些是起点，不是所有链路固定上限。总量上限外，还可给服务、知识库、Pipeline 或模型账号设子上限，防止一类任务耗尽共享资源。手动任务优先于普通自动任务；两类任务同时等待时至少每四次调度给自动任务一次机会，避免饥饿。

调度器先查询在途任务的远端状态。一篇进入终态，事务性记录结果并释放解析槽，随后从该槽可执行的最早待解析任务立即补位；有积压时约每 5 秒检查一次，无积压时约每 15 秒检查一次。只轮询在途 ID，网络请求并发有界。质量暂缓、剔除释放槽位并继续首轮；真实限流、欠费或持续服务故障仅对受影响的池／模型通道实施退避或熔断。旧教育导入器的“泛化排队文字→120 秒等待”逻辑不进入通用调度器。

首轮优先新任务，不即时重跑质量裁决。第二轮先处理不确定写入、模型输出与证据校验问题、真正技术失败和暂缓；剔除项按裁决依据审计，误剔除再重评，明确范围外保留原裁决。重评记录新的尝试、Pipeline 版本和来源证据，不把旧失败回执改写成从未发生。

## 接入与迁移顺序

1. **当前教育批次**：维持正在运行批次的锁与 JSON 回执。修正错误退避、优先补正文解析槽，再处理图片和 artifact。切换进程前核对全部 `upload_intent`、`parse_intent`、在途和不确定任务的远端状态；不重复发送不确定写入。
2. **通用队列试点**：建立 SQLite WAL 任务库及教育适配器，用新的已预处理教育论文验证上传、解析、补位、崩溃恢复和结果分类。当前活跃批次只在安全边界迁移，已经确认的回执逐项导入并核验。
3. **现有入口接入**：让自动按专业交接和工作台手动上传提交到同一队列。迁移期旧同步调用可等待本次提交范围内的上传终态后返回原有上传数量；新的异步入口返回任务 ID，界面查询“已排队／上传中／解析中／终态”，仅在远端回执确认后显示“已上传”。保留各自路由和审核门槛；已有财会论文、财会 Pipeline DSL 与知识库不重写。
4. **后续新专业**：只新增路由／预检／解析／结果／后处理适配规则，不复制调度器。所有新上传使用同一状态和吞吐统计口径。

## 并发压测和验收

客户端在途数与 RAGFlow 服务器实际执行数分别测量。记录上传等待、解析排队、真正执行时长、每小时终结量、成功论文耗时中位数与 95 分位、限流、超时、技术失败和质量裁决；RAGFlow `FAIL` 总数不作为技术失败率。先在有待解析积压的样本上测 3 槽，再试 6、9 槽；每档约 30 篇用于发现问题，约 100 篇用于确认稳定吞吐。若客户端在途增加而远端执行数不增加，检查 RAGFlow worker、模型额度和向量索引容量，不继续堆提交请求。

验收条件：

1. 同一服务、知识库、来源和角色不会因自动／手动入口并行、超时或重启而重复上传；不确定写入先对账。
2. 有合格待解析任务时，解析终态在下一轮短轮询内补位；暂缓／剔除不会造成 120 秒误等待。
3. 财会和教育各自的目标知识库、主文档解析条件、质量裁决、来源身份及 artifact 规则保持正确；图片任务不会占正文槽。
4. 手动任务能优先执行，自动任务不会长期饥饿；一个服务或模型故障不会错误暂停无关目标。
5. 压测报告给出端到端吞吐、远端真实并发和技术失败原因，再确定长期并发上限。十万篇若以 30 天为目标，需平均约 139 篇/小时；此数字是容量规划示例，并非性能承诺。
