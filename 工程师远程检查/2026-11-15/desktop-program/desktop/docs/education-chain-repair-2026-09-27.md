## 服务器修复与真实论文复验

取得用户提供的连接授权后，核对了部署源码和实际 traceback。MySQL 1213 发生在最终执行日志的 INSERT/count/prune 事务，具体冲突语句为保留最新 1000 条时的 `DELETE ... id NOT IN (...)`。模型与索引已经完成，日志失败却使整篇状态变成 FAIL。

最初仅加事务重试仍不足；增加同教育库日志串行后，小日志八并发通过，但真实论文暴露出 15 秒锁等待超时。进一步检查执行计划发现，原 DELETE 按主键范围估计扫描 2759 行；改为先确定过期 ID，再按这些 ID 删除，单条过期记录只扫描一个主键。最终同时保留有限死锁重试、原日志 ID、事务内锁归属校验及物理连接清理。

锁忙异常改用明确的 RuntimeError，避免被外层异步超时包装成误导性的“10800 秒超时”。本地诊断识别已绑定执行的精确数据库日志异常，释放名额并保留技术复核，不触发模型切换。

另发现一篇正文两个章节含相同文本，原来的 text + document ID 使两条正文互相覆盖。仅教育正文/索引的缺省分块 ID 加入章节、分段和重复出现序号；现有显式 ID、assets 和其他库沿用原规则。该文档离线真实回放由 134 条恢复为 135 条，严格来源校验由失败转为通过；线上沿用同一文档 ID 重解析后也通过，没有放宽正文证据校验。

补丁安装器位于 `server_patches/`，有部署源码哈希门控、原文件备份、幂等安装及持久启动调用。只在确认没有进行中的文档后重载了两个执行器，保留原有执行器参数。

- 真实大小约 12.7 MB 的 DSL 八并发通过；模拟事务开始时丢失数据库会话，两个写入均在 INSERT 前被阻止，测试表没有新增记录。
- 链路相关回归 261 项、14 个子测试通过；随后最终连接清理版本单独验证 21 项、3 个子测试通过。上传回执核对新增回归与相关调度测试 22 项通过。

### 后台恢复

2026-09-27 03:40（北京时间）恢复原有通用队列，隐藏进程 PID 33952。维护暂停已解除；现场看到 8 篇解析在途、2 个上传在途，352 篇入库且产物完整，58 篇暂缓、6 篇剔除、0 篇技术复核、0 篇结果未决。队列还在接收工作台已准备好的任务，因此待处理数量会变化，不能与较早快照直接相减当作吞吐。

接管时发现两条上传未保存回执，已通过远端原文件 SHA256 与本地完全一致后补回原文档 ID，没有重复上传。也补齐了通用 Gateway 默认的远端原文件读取，使后续相同情况能够只读核对；读失败或哈希不一致继续保留不确定状态。

恢复全量后，学校接口出现 HTTP 503（Service temporarily unavailable）；现有 RAGFlow 生成模型封装记录了约 113–195 秒的内部退避重试。部分文档随后得到有效暂缓裁决并释放名额，队列继续补位。此项上游波动会显著降低持续吞吐，因此不能将八篇短测折算值当作当前稳定速度。此轮未调整供应商重试策略。

当前调度额度为 6 + 2；服务器两个执行器的执行名额仍为 1 + 2，不能把八个在途名额理解为八个模型同时计算。进一步提升长期吞吐应以服务器执行并发及稳定运行窗口衡量。

两种上传模式均保留：处理前选库自动入队；或处理后在 RAGFlow 处理结果页选论文库和图片库再上传。它们在本机均进入同一通用队列。图片及投影只上传，不发起解析。
