# 第四状态服务端优化：隔离实现计划

用户已授权继续修复三步，要求不影响运行中的真实项目。只在本目录创建或修改隔离候选；不切换、重启或修改真实服务、真实数据、并发配置、任务控制，不访问真实写入端或调用真实模型。保留既有请求、论文、文档、切片及回执身份，保留原始资料。

## 已核实可复用

- 原生 `RagPublisher` 和 `recovery.py` 已有封包、intent、原对象回查和逐条回执；未知结果必须继续保留，不新建原文档、不盲目重发或调用画像模型。
- 当前容器只读源码的 `OllamaEmbed.encode` 支持多文本，`task_executor` 已有批量向量和分批 ES 写入；当前 Prefect 通道未自动接通它们。
- 原生 dataflow 的文本向量与直接切片接口 `0.1*标题+0.9*内容` 规则不同；直接复用不等于数值一致。当前只读源码来自服务容器，不等于已核验执行器容器加载身份。
- 完整线程化候选有文档变更竞态；局部候选 ES 仍阻塞。现有持久 gate 是实验，尚未覆盖真实服务所有写路径。

## 可验收任务

1. **恢复终态保护**：候选客户端对已有 intent 且切片可读的情况，必须验证服务端完整操作终态、文档／切片／内容身份和计数状态；不支持或不确定时保留待核对。先用原现有模拟和新增反例证明缺口，再修复并验证操作未结束不可启用、终态确认后可复用原对象完成、全程不重复发送同一切片和不调用画像模型。
2. **原生批量兼容**：复用现有批量模型、ES 和正文封包，在隔离路径保持逐片同样的标题／内容组合、次序、模型维度和原始文本，限制每批条数及总 token，逐项对账。先以固定向量和真实函数对照测试，再实现最小候选；不把通用 dataflow 的原有行为静默改掉。
3. **服务端完整写入边界**：将分发、终态与计数绑定为可持久查询的操作；排查并覆盖禁用、删除、权限、后台与未知 ES 写入。须独立核查所有共享入口及 MySQL/ES 故障，未覆盖前禁止部署。
4. **集成验收**：2／4 限流、取消与未知超时、批量部分失败、读取及检索、逐篇 NAS 准入与原资料保留，仅使用隔离测试数据和临时服务；核对候选变更及测试由独立审查者复核。

## 明确限制

本地成功和模拟时延不代表当前任务已启用或真实服务器已提速。若服务端无法提供可靠操作终态，客户端保守等待，不依赖单次读回推定成功。单独开启一个候选入口不能阻止旧服务及后台路径写同一文档；必须隔离测试对象或由全部相关入口遵守相同协议。任何外部部署、配置切换和真实任务操作均不属于本次验证。
