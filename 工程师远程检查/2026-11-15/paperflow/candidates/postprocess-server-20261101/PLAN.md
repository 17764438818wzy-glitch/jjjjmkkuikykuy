# Server postprocessing migration implementation plan

**Goal:** Run the existing paper and attachment postprocessing on the LAN server while preserving the existing Prefect folder order and task controls.

**Architecture:** Keep the existing Windows intake and task-control database authoritative. Hand an explicitly identified, hash-verified processing snapshot to an isolated server executor; keep original evidence unchanged and return an independently verified result receipt to the same folder order. Do not reactivate the old scheduler, issue model requests, upload to RAG, or automatically run real folders during installation.

**Technology:** Existing Python postprocessing adapters and renderer; Prefect 3.9; server Linux Python and the existing offline tokenizer artifacts.

## Constraints

- One folder is the existing small order; do not create a second folder order.
- Preserve the current processing granularity: one Prefect TaskRun, durable claim and postprocessing slot per folder; within it, process all body responses, then each attachment, before one folder receipt. The current batch starts at most eight folders and waits for the full batch before the next batch.
- Preserve the existing dedicated Prefect postprocessing limit of 8; a configured limit is not a measured throughput.
- Preserve task/folder/receipt identity, request identities, saved response bytes, image bindings and all hashes; a partial or unknown result must not become an automatic retry.
- A Windows control SQLite database and its file locks remain one authority; never operate on a copied live database or claim a Linux PID is a Windows PID.
- Do not edit upstream artifacts, originals, existing model responses, unrelated candidate code, or running applications.
- The postprocessing and RAG barriers remain closed until the existing authorized control path permits a real job.
- Build and first verify new artifacts in isolation using synthetic materials. The user authorized testing after migration; any later real test must retain the original eligible small ticket, follow the existing controls and never resend an LLM request or upload to RAG as part of this work.

## Work and checks

- [ ] Confirm server and host are separate resource domains; inventory server CPU, memory, disk and existing runtime dependencies without disturbing services.
- [ ] Define an immutable cross-machine input snapshot and path mapping. Tests must reject tampered, missing, aliased, unbound or traversal paths while retaining the original evidence bytes and IDs.
- [ ] Adapt the existing body and attachment processors for server-local input paths and output paths, including complete segment order, original/sent images, tokenizer identity and package validation; do not call combined legacy request entrypoints.
- [ ] Build a CPU-only server execution environment in its own directory and verify the real offline tokenizer with fixed non-paper inputs against the existing tokenizer.
- [ ] Bind server execution to the existing control/identity/gate system and explicit worker-host identity. Persist remote request intent, outcome-unknown states and output receipts so interruptions cannot duplicate work.
- [ ] Verify using synthetic materials and an isolated Prefect/control database that pause/delete, idempotency, incomplete responses and remote failures preserve the original order and do not issue model or RAG requests.
- [ ] Install the server executor without starting real postprocessing or changing RAG gates; independently check its code, dependencies, effective execution location, configuration, failure handling and current live state.

## Review focus

- Saved request/image evidence and Windows paths must remain provably tied to the source instead of being silently rewritten.
- A model response, an upstream registration, a local coordinator receipt and a server output receipt are distinct identities.
- Two machines cannot safely share PID assumptions, SQLite WAL state, or unverified local file locks.
- Interruption during transfer, execution or receipt publication must not be reported as success or retried as a new job.
- Existing RAG, gateway and Prefect services must remain untouched; resource limits and actual server capacity are separate claims.
