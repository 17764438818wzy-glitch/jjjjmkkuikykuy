## Prefect 工单

- 新方案让一个页面任务对应一个 Prefect 大工单；分类通过、交付并登记的资料对应等待前处理的小工单。大工单建立未确认时，页面提示草稿待核对，不当作创建成功。
- 新方案按资料组提交 Prefect 分类任务，一个结束后补上下一个，不再按 500 组一批等待。现有分类执行名额为 8；原来的任务资料组总数上限 30000 仍在。旧版入口仍保留原来的 500 组代码。
- 目前小工单只负责登记为“等待前处理”，还没有接管后续前处理执行。旧下游派单器必须加载排除新工单的代码后，才能与新方案一起安全切换。
- 当前配置仍指向原来的本机 Prefect，未启用新工单模式；已经运行的进程也未重新加载。旧运行入口仍有 500 组分批。因此不能说新工单或 500 组调整已经在当前运行任务上生效。网页静态文件和按需导入的模块可能读取到新磁盘代码，不能一概认为所有旧进程完全不受文件同步影响。
- 新方案的代码已同步到当前第一步和接收代码，恢复版代码也保留；切换仍需要同步调整执行器、接收进程和旧下游派单器，并核对是否存在旧任务。切换、部署、重启及功能验证本次均未执行。同步前的原文件和逐文件摘要保存在同目录下 `sync-backups-20261031-164907-5ca8ef`。
- 新模式暂不接管旧模式建立的任务；切换时必须先处理旧任务，不能直接把旧任务当作新工单使用。启动写回异常时，同一 API 进程内会把该次启动标为待核对，不自动重复提交；跨 API 进程的异常恢复尚未验证。

## 恢复版原有的锁

| 原有协调 | 这次的代码处理 | 原因或保留范围 |
| --- | --- | --- |
| 任务锁 `task-<任务>.lock` | 新工单的开始和资料状态更新等路径不再持有；上传、选取资料、删除仍保留 | 不在联系 Prefect 时一直占有任务锁；上传和删除还要协调同一批文件。 |
| 前处理交接锁 `preprocessing-<任务>.lock` | 保留 | 旧下游领取和暂停分别涉及不同数据库，尚未由一套统一交接事务接管。 |
| 上传锁 `upload-<上传>.lock` 及上传计数小锁 | 保留 | 协调上传、结束上传和删除。 |
| 全局登记锁 `first-step-registration.lock` | 保留，尚未完成目标改造 | 同时保护登记记录、回执文件和删除时的共享引用检查；不能只把锁删掉。 |
| Nimble 进程内 `_MODEL_GATE` | 从磁盘上的第一步代码中移除，运行进程尚未重新加载 | 已检查主要调用链外层还有 `_nimble_request_gate`；下方的跨进程请求锁也仍在。 |
| Nimble 进程内 `_nimble_request_gate` | 保留 | 当前请求入口尚未全部改为由 Prefect 统一安排。 |
| Nimble 跨进程 `nimble-requests.lock` | 保留 | 仍存在不完全受新工单约束的入口；仅移除 `_MODEL_GATE` 不会提高并发。 |
| 资料组分类锁 | 保留 | 不同任务和手动入口可能处理同一源文件夹；仅有任务工单不能覆盖这个情况。 |
| Office 转换名额锁 | 保留 | 转换入口尚未全部接入统一 Prefect 名额。 |
| WPS 共享锁和转换缓存锁 | 保留 | 协调共享转换程序或同一份缓存的写入。 |
| 等待队列 `.scan.lock` | 从磁盘上的接收代码中移除，改用已有 `.watch.lock`；运行进程尚未重新加载 | 已检查的扫描和循环接收入口统一用现有接收进程锁。 |
| 等待队列 `.watch.lock` | 保留 | 防止旧接收进程重复扫描、接收。 |
| SQLite 数据库写入协调 | 数据库机制保留；普通状态查询改为先只读，确有失效状态时才写 | 新方案的模型请求发送仍会短时间占用写事务，其他写入和暂停可能等待。 |
| 服务管理锁、日志和小缓存锁 | 保留现有需要的部分 | 主要协调服务启动或进程内部数据，不是资料逐个排队的任务锁。 |
| 后续前处理中的文件夹、论文、领取和小工单锁 | 保留 | 旧下游尚未由新小工单接管，覆盖对象和共享资源也不完全相同。 |

旧候选额外出现的 `order-submit-<任务>.lock`、统计缓存锁 `_summary_lock`、`nimble-start.lock` 没有带入新方案。它们不是说已经从正在运行的恢复版进程里撤掉：其中有的本来就不在恢复版的已检查路径中。

这次没有新增任务保护锁。登记锁、交接锁和后续处理锁尚未达到可以撤掉的条件；没有把它们描述成已经移除。
