# H2.1 第三状态：正文画像与附件意图识别

本文件是第三状态接口说明。联合验收和正式源代码合并状态以 verification/ 下报告及最终实施报告为准。

## 对用户和第四状态的交付

正文仍按原 MD 模板画像。附件先经过附件意图识别 LLM（或复用同一附件、同一身份的有效成功结果），识别类型、简单说明、依据和限制。程序将这些结果与原件身份、读取事实和包内目录合成 **一份 attachment.md**。每个原附件只交“原件＋这一份 MD”；一 RAR/ZIP 整包是一项，包内成员只有目录行。

Nimble 负责上游分流，不能用其分类概率代替附件意图识别结果。MD 渲染不调用模型。原 description.json、回答和请求台账只用于内部追溯，第四状态无需拼接第二份说明。内部 delivery.json / deliveries[] 仅用于传递路径、版本和哈希，不是另一份必交业务文档。

格式与第四状态的 `附件交付模板_v1.md` 对齐：开头 schema=attachment-card/1，固定 paper_id、attachment_id、source_name、source_format、source_bytes、source_sha256；后面依次为附件类型、简单说明、读取依据与限制、包内目录。上游不填 RAG 库 ID、下载链接或 NAS 回执。

目录五态：complete / partial / unavailable / not_archive / not_read。只有确认没有尝试读取才用 not_read；读过未保存或历史是否读过未知用 unavailable 并说明。目录完整不表示成员内容已读。type 未核实的条目不伪装成 file/directory；MD 只列类型已核实的项，listed_entries 按实际表行计数，total_entries 保留原可靠总数或 null。

正文内联文本和目录单元格：先把原始 % 编为 %25，CR/LF 编为 %0D/%0A，再作 HTML 字符转义，Markdown 特殊字符使用十进制 HTML 实体。消费者对原始单元格仅作一次 HTML unescape、再作一次 percent unquote。元数据使用 JSON 标量（合法 YAML），不应用正文解码。

## 接收入口

窗口 1 使用 `paperflow-group-handoff/2` 及独立 `attachment-evidence-handoff/1` 证据；窗口 2 的 `ReceiptStore` / `receive_handoff` 冻结正式身份和逐项接收回执。第三状态只消费已接收项，正文可为 null；垃圾不进入第三状态。新第三状态入口止于画像及附件 MD，不调用第四/五状态。

```powershell
# 只读检查回执，不读凭据、不发请求
.\.venv\Scripts\python.exe -B -X utf8 stage3_handoff_cli.py check --receipt <接收回执.json>

# 对一项确认为首次处理的材料核对历史；不会发请求，也不会清除旧请求。
# 必须列出相关历史数据根目录；遗漏的历史位置不能靠这个命令推断不存在。
.\.venv\Scripts\python.exe -B -X utf8 stage3_handoff_cli.py confirm-first-request --receipt <接收回执.json> --file-id <正式文件编号> --history-root <原数据根目录>

# 明确执行第三状态；仍受现有 execution_enabled 与 Prefect 并发约束
.\.venv\Scripts\python.exe -B -X utf8 stage3_handoff_cli.py process --receipt <接收回执.json>
```

正常续跑会先定位历史工作目录；已完整的结果复用，旧完整回答只作确定性语法恢复。unknown 请求、来源冲突或无法定位历史时停止该项，不通过换论文号/模型配置/输出目录重发。首次请求核对不是“忽略历史”的开关：已发现请求、旧回答、身份冲突或不可核验记录都会阻断。相关历史根目录的完整性必须由接收映射负责，不能把来源迁移当作新资料。

供编程调用：`flows.received_handoff(receipt_path)`；无 Prefect 的离线依赖顺序可测试 `workflow.execute_stage3(paper, call)`。正式入口不要直接用测试替身或低层函数绕过接收和模型调度。

## 复用与保留

- 原 body_signature 算法及其配置、原 MD 模板不改变。正文成功缓存直接返回，不重新准备或画像。
- 接收给出的历史目录优先于当前模型签名。新增 source-work-bindings 固定原件与工作目录的关联，模型配置变化不能把旧请求放到一边。
- 新证据只追加版本，第三状态检查全链；当前 sidecar 以接收回执保存的路径和哈希核验。文字、目录、图片逐条以共用验证器的 verified 为准；历史来源未核实时保留限制，不能冒充已读证据。
- 新附件确有必要时复用现有本机预览；最多使用四张已核验图片，不把整包二进制直接交给模型，不执行包内程序。DWG 等无可用预览的格式保留读取限制与不确定结论。
- 模型只收到有界证据投影，JSON 序列化后的主要文字上下文不超过24000字符，含图片编号的文字合计不超过26000字符。完整目录保留给 MD，不在请求中重复附带。新请求用版本化投影核验；旧请求继续按原始格式读回，不重写旧 evidence/request。
- 每个 MD 版本独立保存；旧说明、原回答、请求、证据和旧 MD 不覆盖。新增证据不能被写成旧模型已经看过。
- 识别成功与附件 MD 生成、RAG、NAS 分开记录。后续失败不会再次发起画像或附件识别。

## 验证边界

测试使用隔离原件、模拟模型响应及本进程临时 HTTP 服务；不向业务模型、RAG 或 NAS 发送请求。真实 100 份只做只读缓存与哈希检查。主 runtime 没有可复用的真实完整附件说明样本，不能把模拟附件测试说成真实附件验收。

本次接收合同未建设独立的历史文字/目录来源台账及图片来源台账。因此仅有 sidecar 自报来源的旧证据继续降级，不从这些字段直接构造信任。当前实际读取并由接收回执冻结的文字/目录，以及第三状态实际生成并核验的本机预览，可按规则使用；这与“历史图片复用已全部接通”不同。

第四状态目前完成了格式对齐和模板更新，MD 接收校验与原件下载链路仍由第四状态接入。本轮不实现其运行逻辑，也不重启现有服务。
