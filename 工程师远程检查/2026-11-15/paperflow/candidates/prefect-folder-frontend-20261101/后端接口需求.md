# 前端需要的大小工单接口（候选约定）

工单窗口的 `CONTROL_HANDOFF.md` 已发布候选 HTTP 路径和字段；以下约定及隔离检查**不代表已上线或已完成真实联调**。本地静态配置 `tasks_api_url`、`folder_tickets_api_url`、`control_api_url` 均为空，不接回旧队列或旧控制。

候选统一启动入口使用 `http://127.0.0.1:8796/` 提供页面，并由 `/api-config.json` 按页面当前来源动态生成三个绝对地址；静态文件仍保留空值。调度窗口报告该入口已加载，实际状态以总交付报告为准。下面的示例仅说明拼接关系：

```json
{
  "tasks_api_url": "https://example.invalid/api/v1/prefect/tasks",
  "folder_tickets_api_url": "https://example.invalid/api/v1/prefect/folder-tickets",
  "control_api_url": "https://example.invalid/api/v1/prefect"
}
```

前端再用根地址拼接自检、创建、分类、开始/暂停和重试路径。静态文件的三个字段均为空；如在只读联调中单独提供配置，可将 `control_api_url` 留空以避免启用操作，但第一步分类也依赖该地址，这时同样无法读取。页面须以固定的本机 `localhost`/`127.0.0.1` 来源或 HTTPS 提供，不直接用文件路径打开；跨源时后台需允许该页面来源。创建请求依赖安全环境的 `crypto.randomUUID()`，创建/重试待核对标记存放于当前浏览器来源，切换主机名、协议或端口会改变本地存储。统一入口尚未完成真实加载验收，结果未知时不得靠切换来源重新提交。

## 任务选择

需要只读任务列表，供用户选择当前大工单。候选前端使用的示例：

```json
{
  "as_of": "2026-11-02T10:00:00-08:00",
  "complete": true,
  "tasks": [
    { "task_id": "task-A", "task_name": "任务甲" },
    { "task_id": "task-B", "task_name": "任务乙" }
  ]
}
```

`task_id`、`task_name` 为字符串；`complete` 表示列表是否完整；`as_of` 使用带时区的 ISO 8601 时间。接口不可用时显示不可用，列表不完整时明确提示；前端不会自动选择任务，也不凭空生成任务。

## 当前任务的论文小工单

需要按所选 `task_id` 只读查询一个大工单的快照。建议形式为 `GET /api/v1/prefect/folder-tickets?task_id=task-A`；下面仅是合成示例：

```json
{
  "task_id": "task-A",
  "task_state": "running",
  "desired_state": "running",
  "actions": {
    "start": { "allowed": false, "reason": "任务已开始" },
    "pause": { "allowed": true, "reason": null }
  },
  "stop_reason": null,
  "detail": null,
  "as_of": "2026-11-02T10:00:00-08:00",
  "complete": true,
  "folders": [
    {
      "ticket_id": "该论文的 Prefect 小工单 ID",
      "task_id": "task-A",
      "folder_id": "资料文件夹 ID",
      "folder_name": "资料文件夹名称",
      "paper_title": null,
      "task_name": "任务甲",
      "stage": "llm_in_progress",
      "failed_stage": null,
      "failure_detail": null,
      "retryable": null,
      "retry_reason": "失败点尚未接线",
      "last_retry": null,
      "llm_body_running": true,
      "llm_attachment_running": true,
      "preprocessing_result": "passed",
      "llm_result": null,
      "postprocessing_result": null,
      "preprocessing_detail": null,
      "llm_detail": null,
      "postprocessing_detail": null
    }
  ]
}
```

- 顶层和每条记录的 `task_id` 必须是所选大工单；不得混入其他任务。每个合格论文文件夹只返回一条，阶段运行记录和历史重试不能各算一篇。`ticket_id` 是贯穿全程的同一小工单 ID。
- 后续队列展示需求是将 `complete` 用于判断**当前小工单列表是否读取完整**，并将单篇 `unresolved` 位置单独说明；这不表示全部分类完成或任务完成。窗口 1 正在调整后台候选；用户要求先验证任务运行，前端本轮试制已恢复，当前页面仍将包含 `unresolved` 的快照整体视为不完整。列表不完整时，非零显示下界、未知零显示待核对。`as_of` 是快照观察时间，后续再对齐最终接口并验收。
- `task_state` 是后端确认的大工单实际状态；只有分类结束且全部应处理论文完成入库、NAS 和本机清理，才能返回完成。`desired_state` 是大工单期望的开始/暂停状态，两者不能互相冒充。候选当前识别 `created`、`waiting`、`running`、`paused`、`completed`、`failed`、`unrecognized`、`unresolved`；**请后端确认最终枚举和含义**，未识别的值显示“状态待核对”。
- `actions.start`、`actions.pause` 各包含布尔 `allowed` 和字符串或 `null` 的 `reason`；页面据此控制按钮并显示不可操作原因。缺少许可时只显示数据、禁用操作，不根据状态猜测。后端仍在开始时重新自检。
- `stop_reason` 可选，返回大工单自身的停止或公共依赖故障原因，例如模型服务不可用；它不是某篇论文的失败原因。没有原因时为 `null`。
- `paper_title` 是已确认题目，没有确认时返回 `null`；`task_name` 可选。`folder_id`、`folder_name` 和 `ticket_id` 为字符串。
- `llm_body_running`、`llm_attachment_running` 为布尔值或 `null`。`null` 表示运行状态未知，不能当作 `false`；即使列表 `complete=true`，前端也独立显示该活动数为下界或“待核对”。正文与附件可以同时处理，两个值可以同时为 `true`，工单总数仍然是 1。一个组件失败时另一组件可能还在收尾，前端同时展示失败和已确认的运行活动，不将两项相加当成两篇。
- `preprocessing_result`、`llm_result`、`postprocessing_result` 分别取 `passed`、`failed`、`unrecognized` 或 `null`。`null` 表示该阶段没有可确认的结果；结果未知时不能冒充失败或通过。**由后端确认整篇必要回答完整保存、包含基于全文的最终专业判定后，返回 `llm_result: "passed"`，不等后处理；后处理结果独立返回。**分段只是处理材料的方法，局部榜单不能当成整篇最终排名。
- `failed_stage` 在 `stage: "failed"` 时填写 `preprocessing`、`llm`、`postprocessing`、`rag`、`nas` 或 `cleanup`，其他状态可为 `null`。`failure_detail` 为对应失败原因，可选；前三阶段各自的 `*_detail` 可选，没有时为 `null`。前端不会编造原因。
- 候选后端使用 `retryable` 及 `retry_reason` 表示是否可重试和原因；前端仅在配置控制接口、`retryable: true` 且快照包含 `last_retry` 时允许用户确认后手动提交。候选后端已可对满足条件且已停止的论文小工单允许重试，仍需逐阶段真实验收。响应确认原任务、文件夹、小工单、重试编号和 `scheduled` 后，或用户只读核对到符合身份的新重试时，清除本地待核对标记；未知时保留标记，不自动重发。

候选前端目前接受的 `stage` 值如下，最终枚举以工单窗口实际接口对齐：

| 值 | 页面位置 |
| --- | --- |
| `waiting_preprocessing` / `preprocessing_in_progress` | 当前等待前处理 / 当前前处理中；登记即进入等待，实际开始前处理后离开等待。累计登记数单独按本次快照的小工单列表计数，不用两个阶段数之和冒充 |
| `waiting_llm` / `llm_in_progress` | 等待 LLM / LLM 处理中 |
| `waiting_postprocessing` / `postprocessing_in_progress` | 等待后处理 / 后处理中 |
| `waiting_rag_upload` / `rag_in_progress` | 等待 RAG 上传 / RAG 处理中 |
| `waiting_nas_archive_delete` / `nas_in_progress` | 等待 NAS 归档 / NAS 归档中；前者名称沿用旧候选字段，不表示本机清理已开始 |
| `waiting_cleanup` / `cleanup_in_progress` | 等待本机清理 / 本机清理中；候选后端已使用这些字段值 |
| `completed` | 这篇论文全链路完成，包含全部选定目标入库、NAS 归档和本机清理 |
| `failed` | 确定失败，配合 `failed_stage` 和失败原因展示 |
| `unresolved` | 小工单当前位置待核对；不能显示为成功或自动重发 |

暂停以最后准入为界：已获准的单个请求可以发出并收尾保存；后续请求仍需重新准入。页面按实际位置显示，不能把尚未开始的新步骤显示成运行中。前端不根据局部阶段结果自行推断整个任务成功。

## 第一步分类结果

工单窗口候选已提供 `GET /api/v1/prefect/tasks/{task_id}/classifications`，返回 `task_id`、`as_of`、`complete`、`items` 和 `counts`；每条 `items` 含资料组、文件夹、题目、`status` 和原因。前端候选按所选任务的 `items` 展示已通过／失败／未识别／待核对及对应列表，数量与列表使用同一批记录。候选后端依据分类完成回执及记录数量计算 `complete`；不完整时无法确认的零显示“待核对”，已知非零显示下界。

第一步分类失败或未识别的文件夹可能尚未产生小工单，因此不能从后续论文小工单反推第一步结果。候选接口读取已保存的分类回执，真实资料的分类来源和结果仍需验收；接口不可用时前端显示不可用，不显示假零。

## 自检和操作接口

候选后端提供 `POST /api/v1/prefect/preflight`、`POST /api/v1/prefect/tasks`、`POST /api/v1/prefect/tasks/{task_id}/start` 和 `/pause`。前端按这些路径接线，静态配置为空，统一入口动态提供配置。本轮通信修复后，自检、创建、开始、单篇重试、完整工单列表、任务列表及按创建请求号查询的浏览器等待为 120 秒；轻量分类查询及暂停维持 8 秒。工单列表每次读取未完成时，定时器不重复发起同类读取；操作后仍重新读取当前状态。控制接口的动作落实后立即确认由窗口 1 处理，前端继续按 HTTP 响应判断，超时不自动重发。自检展示每项实际返回的名称、就绪状态及原因；创建由后端再次检查。创建请求包含 `request_id`、`task_name`、`source_paths`，前端在发送前保存 `request_id`；结果未知时保留该编号、阻止自动再建。

候选后端新增 `GET /api/v1/prefect/tasks/by-request/{request_id}`。前端在用户点击“核对创建结果”后使用原编号查询：找到且确认时打开返回的任务并清除本地待核对标记；未查到、查询失败或返回不匹配时保留编号，不自动创建。当前 `found=false, resolved=false` 仍是未知，不代表确定未创建；如要支持这种情况下解除标记，后端还需提供能排除请求仍在执行的可靠结论，不允许靠换编号绕过。大工单操作能力已使用候选 `actions` 字段，仍需最终接口及真实状态验收。

后端候选已实现执行进程、模型、RAG、NAS 等依赖的只读检查，但尚未在正式服务执行，相关检查也不等同于真实推理或写入成功。候选 `pipeline` 按入口和部署配置检查结果返回，不能据此认定真实业务全链已完成。单篇重试会在满足条件时调度原小工单，失败和未知结果仍需后端核查。

候选工单快照的 `last_retry` 为 `null` 或 `{retry_id, stage, status}`，状态包括 `scheduled`、`running`、`completed`、`failed`、`dispatch_unknown`、`unresolved`。前端提交前保存当前小工单及旧重试编号；响应未知后，用户可主动读取现有工单快照，只有同一小工单出现不同于旧记录的新编号且状态明确，才解除本次待核对。若响应另给出了本次编号，还必须匹配该编号。旧成功、记录缺失、不同工单、未知状态或读取失败都不能解除；旧版仅保存 `1` 的标记缺少身份，须联系后端核对。工单已变为运行、完成或暂未出现在快照乃至快照读取失败时，待核对入口仍保留。核对仅 GET，不自动重发。

HTTP 409 的结构化 `detail.code` 中，`retry_not_allowed`、`paper_not_stopped`、`retry_already_dispatched` 表示本次提交在派发前被拒绝；自检明确未通过同样是拒绝。前端清除本次标记并显示后端原因。`retry_dispatch_unknown` 保留标记和返回的 `retry_id`；未知代码或旧式 409 也继续待核对。以上依赖后端维持该候选契约。

文件夹选择/上传接口和“删除整个任务”的语义尚未确定，不从逐篇清理规则推断。跨源读取时由后端允许候选页面来源。所有在线 API 仅在后续实际联调时配置；本次检查只使用合成数据。
