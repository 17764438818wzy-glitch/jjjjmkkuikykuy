## 前处理到正文识别

新前处理按当前容量配置先判断整篇是否可放入；确需分段时，使用原有章节、文本块等自然边界规划，记录主材料范围和资产归属，并检查主范围覆盖。容量估算和真实通道能否接受请求是不同的事实；规划不代表模型已经读取。

运行代码的 `paperflow-local-preprocessing-handoff/1` 包含正文材料、阅读材料和哈希，并在 `capacity.plan_identity` 中绑定模式、各段请求摘要、范围摘要和整体覆盖摘要。LLM 执行前按这份身份核对计划；规划不可用或历史请求无法确认时，保留记录并停止，不能当作一段或零段。同步后的这条交接尚未由用户的真实任务测试。

## 模型原始回复

正文提示词要求模型返回一个 JSON 对象，而不是直接输出 Markdown。预期字段遵循 `paper-preextract/1.0`：`source`、`profile`、`tree`、`assets`、`redaction_plan`、`gaps`、`segmentation`、`attachments` 等。正文分段时，各段分别保存原始回复及其对应范围和请求证据。原始回复完成只说明传输完整；未经后处理解析、校验，不能保证它是合法 JSON 或语义正确。

单次输入的原始正文回复保存在正文工作目录的 `model/response.txt`；分段时分别保存在 `model/part-001/response.txt`、`model/part-002/response.txt` 等目录，并保留分段计划、请求状态和响应事件。每份附件的原始回复保存在该附件工作目录的 `model/response.txt`。具体工作目录由已登记的来源与历史绑定决定，不能仅凭文件名猜测。

附件每项的原始识别回复预期是一个 JSON 对象：

```json
{
  "kind": "附件类型",
  "summary": "简要说明",
  "evidence_refs": ["实际提供的证据编号"],
  "limitations": ["未读取或无法确认的范围"]
}
```

附件回复来自该附件可用的上游证据，未提供的内容不能视作已经阅读。原实现会在解析校验后生成带 `paper_id`、`attachment_id` 和来源哈希的 `attachment-description/1`，该解析及后续卡片渲染均不在本次执行范围内。

## 原有后处理生成的 Markdown 参考格式

### 正文 `article.redacted.md`

现有发布程序先按脱敏后的正文块顺序连接块内容，以空行分隔，生成 UTF-8 文本。它不要求固定的 YAML 头；章节、表格和公式以已提取到的正文内容为准，不能仅凭文件名断言原始版式或全部内容均已还原。论文画像、章节结构、资产信息和分段等另外写入 `profile.json`、`tree.json`、`assets.json`、`chunks.json` 等文件，而不全都塞进正文 Markdown。

```md
正文块 1 的内容

正文块 2 的内容
```

这只是连接方式示例，不是现有论文的实际输出，也不表示正文生成或脱敏已经执行。

### 附件 `attachment.md`

原渲染器为每个附件生成 UTF-8 文件，头部是 `attachment-card/1` 的身份字段，正文包含类型、简单说明、读取依据与限制以及包内目录：

```md
---
schema: "attachment-card/1"
paper_id: "论文标识"
attachment_id: "附件标识"
source_name: "附件名"
source_format: ".zip"
source_bytes: 123
source_sha256: "附件文件的 SHA-256"
---

# 附件交付说明

## 1. 附件类型

附件类型
```
