# H2.1 附件证据交接接口（隔离候选）

状态：本接口及分类写入仅在隔离候选实现；尚未合并正式目录或验证端到端流程。接收端和第三状态应复用此模块，不另建第二套证据验证器。

## 验证接口

```python
validate_evidence_handoff(record, handoff=None, *, verify_files=False,
    trusted_image_records=None, trusted_sidecar=None, trusted_evidence_records=None) -> dict
```

- 成功返回 `{"valid": true, "binding_verified": bool, "source_verified": bool, "evidence_items": [...], "images": [...]}`；格式、原清单或原件身份不符时抛出 `EvidenceHandoffError`（继承 `ValueError`）。
- `valid` 仅表示该次所要求的结构检查通过。未给原清单时 `binding_verified=false`，不能用于正式接收或作为模型输入的身份确认。
- 给原 `paperflow-group-handoff/2` 清单时核对组标识、四元组、唯一附件成员及清单版本；不依赖整组必须完成，也不会调用旧正文转换或模型。
- `verify_files=true` 必须给原清单，会核验当前附件原件大小和 SHA-256；只有成功时 `source_verified=true`。未请求文件核验时该值为 false。
- `evidence_items` 逐条报告文字和包目录的 `evidence_id/verified/reason`。`source_verified` 只证明附件原件，**不能证明历史文字或目录属于该附件**；只能将对应 `verified=true` 的证据用于识别。历史证据必须有独立可信台账所固定的记录路径和 SHA，在 `trusted_evidence_records={绝对路径: SHA256}` 传入后，接口再核对记录哈希、条目标识、附件原路径与指纹以及文本或目录内容。此入口当前支持旧 JSON/JSONL 中带 `id/path/sha256/evidence` 的记录；其他来源格式保持未核验。
- 当次读取的目录和文字须由接收端保存并独立核定证据文件及 SHA，使用 `trusted_sidecar={"path": 绝对路径, "sha256": 已核定哈希}` 传入；接口还会读回核对内容与提供的 record 完全一致。不能把由待验证的 sidecar 自行计算的哈希直接当作可信台账。未提供可信记录时保留待核，`verified=false`。
- `images` 报告按输入图片逐项返回 `{"evidence_id": ..., "verified": bool, "reason": ...}`。图片必须由独立可信台账固定来源记录哈希，使用 `trusted_image_records={来源记录绝对路径: SHA256}` 传入；接口进一步核对原附件路径和指纹、来源记录内的图片与位置、图片文件哈希、格式及尺寸。当前支持的来源记录为 JSON，含 `source_path/source_sha256/images`，图片项须完整保存对应属性。缺来源或来源格式无法核验时保留待核、不能送模型。当前分流读取器不会把 PDF 图片数量冒充预览图，也不生成图。
- 此报告不表示历史请求已核验，也不表示附件说明、接收或整个资料组已经完成。历史记录是否可复用由接收/第三状态按各自台账进一步核对。

## 保存接口

```python
write_evidence_handoff(record, directory, *, handoff) -> pathlib.Path
```

要求原清单，并核验本项原件；在资料库以外的指定目录按组及来源四元组保存独立版本。相同记录重试返回原路径，不覆盖旧文件；新版本必须关联前一版本。如果新版本的事实内容与前版相同，返回前版路径。不会修改原清单、原附件或历史模型请求。

`evidence_version` 是同一组及来源四元组内的正整数；`previous_evidence_version` 为第一版的 `null` 或后续版的上一版本号。原清单 `result_version` 独立，不因证据补充而改变。

`read_evidence_history(path, *, handoff, verify_files=False)` 从第 1 版读到指定版并检查连续性、每版来源和清单绑定；任何缺失、跨组或版本不符都会报错。读取整条链后由消费端检查所有历史说明和请求，不得只检查最新一版。

`make_evidence_handoff(handoff, row, *, preview=None, decision=None, provenance=None, decision_provenance=None)` 只转换已取得的证据，不读取原附件或调用模型；`append_evidence_handoff(record, directory, *, handoff)` 在同源已有记录上幂等追加版本。历史目录或文字的来源可能与分类结论的来源不同，必须分别提供；历史证据若没给 `decision_provenance`，不编造分类结论的出处。历史输入不得仅凭调用者提供的内容视为已核验；需使用上述报告逐项检查。

## 分类入口与历史防重

`classify_batch(..., verified_new_groups=...)` 默认不启动历史未知的资料。接收方在查证跨目录历史并确定从未发送后，才可把相应资料组加入 `verified_new_groups`；命令行对应 `--verified-new-group`。已保存的完整清单先核验原组及文件快照后复用，不调用模型；发送前保存不可覆盖的 intent，存在未完成 intent 时不重发。同一输出目录的已保存 sidecar 会随复用结果返回，版本链置于 `evidence_history`。如历史在其他目录，必须由接收端先定位，不能仅因本目录未找到而认定为新资料。低层 `classify_group` 不含请求防重，正式接入不得直接调用它。

同一台电脑、同一用户临时目录内，按规范化后的资料组实际路径取得跨进程独占锁，覆盖检查、intent 和分类调用；同一资料组使用不同输出目录或资料库根目录也不会并发。不同 Windows 用户临时目录、跨机器、跨路径搬迁以及不同输出目录之间的历史定位仍由接收台账负责。资料迁移后，必须先通过接收端稳定身份核对旧路径下所有请求，不能把新路径当作未发送；目前未实现跨用户或迁移身份互斥。证据来源 SHA-256 在 sidecar 中统一为小写，防止同一指纹拆成两条版本链。

组锁使用现有 `filelock`。当前验收环境可用，但项目 `requirements.txt` 没有直接声明此依赖；合并及迁移环境时需由负责依赖的窗口核对并纳入部署依赖。缺依赖时批处理在调用模型前失败，不绕过锁。

## 消费约定

- 接收端先按原组与附件成员建立稳定正式身份，再用本接口核对证据关联；正式论文/附件编号不由本模块产生。
- 第三状态只有在 `binding_verified`、`source_verified` 为真时，才将该记录视为已绑定到当前原件；每条文字、目录和图片还须对应报告的 `verified=true`，不能使用未核验内容。
- 目录 `type=null`、总数未知及无图片预览均可如实交接；不能由此推断类型或宣称完整。旧说明和历史请求原样引用，不能把 Nimble 分流概率当作附件说明。
- 所有证据版本保留；接收和第三状态必须沿 `previous_evidence_version` 查全链，不能因最新版本 `request_records=[]` 或 `existing_identification=null` 就把先前成功或未知请求视为不存在。当前新分流只保存 Nimble 分类参考，不伪造完整请求、已有说明或原模型响应。
- 历史条目的路径须与当前原附件路径一致才能通过内置历史目录/文字校验。资料迁移后，如需沿用旧路径下的证据，应先由接收端验证来源迁移关系；当前实现不会仅凭相同 SHA 自动放行，也不会自行执行迁移映射。
