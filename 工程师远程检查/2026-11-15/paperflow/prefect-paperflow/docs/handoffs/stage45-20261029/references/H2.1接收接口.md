# 接收 H2.1 接口（窗口 2 候选，供窗口 3 接入）

入口：`paperflow_prefect.intake_handoff`。本模块只登记，不调模型，不执行画像、RAG、NAS或调度。

```python
store = ReceiptStore(receipt_root, history_roots=[old_data_root], evidence_validator=shared_validator)
receipt = receive_handoff(handoff_path_or_dict, store,
    evidence_records=[evidence_path_or_ref],
    origin_group_id=None, previous_group_root=None)
inventory = receipt['inventory']  # None 或兼容 prefect-paper/1 的只含已接收项清单
```

`origin_group_id` 只接受账本已有组的明确迁移映射，并把该组已登记的来源目录用于核对旧 inventory，待收附件也能接续旧编号和原工作目录。`previous_group_root` 是调用者明确提供的旧组路径，用于尚未进接收账本的旧 inventory；不会凭同哈希跨组找人。同一个 group_id 换了来源目录也必须有明确迁移映射。

## 返回

- schema=`paperflow-receipt/1`，`state` 只为 `未接收` / `已接收`。
- `group_id` 为本次上游组；`origin_group_id` 为持久来源组；另有 handoff_id/result_version、receipt_id/record_path。
- `items` 含本次正文和每个附件的逐项结果，只有已接收项进入 `inventory`。
- `new_items` 是第一次接收的新原件版本项，不包括重复交接/补证据/仅改交付名称。
- `new_items` 是该次冻结回执的事实，完整重放会返回同一份回执；它不是可重复执行的调度命令。下游应按正式文件 ID、原件修订及原工作台账判断能否推进。
- `retained_trash` / `unresolved` 保留原清单事实；不读取垃圾，不传给第三状态。
- `progress` 为 body_received/body_total/attachments_received/attachments_total/unresolved。
- `batch_summary(receipts)` 按 origin_group_id 去重，只返回 total/received/remaining。
- 统计范围为调用者传入的来源组，不能把一个分批切片的剩余数解释成全库剩余数。接收接口本身没有 10,000 份上限；跨批次由调用者保留冻结组清单和所有批次回执。

## inventory

保留 schema、paper_id、revision、person_dir、library_root、body、body_copies、attachments、archive_files、excluded。

**body 可为 null；attachments 只含已接收附件。** 调用者必须分别推进，不能据此调用要求正文非空的整篇旧入口。

资料组身份充分时，可以先接收附件并确认 paper_id，正文稍后补交仍沿用该号；不以正文是否就绪作为附件接收闸门。

每个有效正文/附件行保留 path、relative、bytes、sha256、kind、file_id：

- `relative` 保留原件来源相对位置，不改为交付别名，也不改变原 body_signature。
- `file_id` 为本次接收确认的正式文件 ID；附件另有相同值 `attachment_id`。
- `upstream_file_id` 保存上游原 ID。
- `source` 为 handoff_id/result_version/file_id/source_sha256 四元组。
- `source_binding` 是 group_id 加上述四元组。
- `handoff_ref={path, sha256, hash_kind}`；直接传 dict 时 path=null，hash_kind=canonical-json-sha256。
- `display_name` 为题目及附件序号的新交付名；不移动、改名或复制原件。
- `evidence_records` 为已经共用验证器核对的 `{path, sha256, evidence_version, source, group_id}` 引用；未核验材料单独保留原因，不冒充可用证据。

## 历史定位：先使用原目录，再考虑任何当前签名目录

每行 `history`：

- `body_work` / `attachment_work`：**单路径 string 或 null**。有多个无法唯一选定的候选时为 null，不任意选一个。
- `work_dirs`：所有已关联旧工作目录的列表，供核对。
- `request_records`：原请求/回答/state 的路径、摘要及观察结果，不改原文件。
- `existing_identification`：唯一可核验完整旧说明的 `{path,sha256,work_dir,source_sha256}` 或 null。
- `existing_identifications`：所有符合原件身份的候选说明引用。
- `policy`：`reuse_complete`（复用原成功结果）、`inspect_saved_request`（已有请求，核对/恢复原记录）、`history_lookup_required`（尚未定位历史，不能当新请求）。这是内部执行约束，不是第三种接收状态。
- `allow_new_request`：接收模块始终为 false。未找到记录不是“从未请求”的证明；首次请求证明和原生请求保护由第三状态明确核对。
- `limitations`：历史扫描/校验限制。

完整重复交接复用已冻结接收结果，不为扫描重复读取原件；实际下游使用前必须调用 `verify_received_file(item)` 再核验原件。接收成功不表示内容读取完整，也不表示已有模型请求可以重发。

优先沿用匹配来源的旧 inventory.paper_id 和旧附件 file_id。旧历史与已登记正式号冲突时停止该项/组的身份确认，不偷偷换号。成功正文历史目录按旧 inventory 中原 relative、source_sha、body_signature 定位；附件按旧 file_id 定位。新增证据不换历史目录。

## 窗口 1 共用验证器

本模块不复制证据 schema 验证逻辑。调用窗口 1 的实际签名 `validate_evidence_handoff(record, handoff, verify_files=True)`；正式合并时导入同包 `attachment_evidence_handoff.py` 及其既有依赖。模块未提供或证据未通过时，原件接收与证据可用性分开，清楚记录限制。`validation.valid` 仅说明该记录通过验证器，内容可用性还要看其中 evidence_items/images 的逐项核验结果；第三状态使用回执冻结的 path+sha 作为 trusted_sidecar 等可信引用再核对，不把结构正确当成内容已读。

一个原件版本可以有多份追加证据，证据通过来源组加四元组绑定；同一 evidence_version 不允许换内容。正式附件号不因补证据改变。attachment.md 由窗口 3 生成，窗口 2 不改写已有说明、请求或回答。

传入 v2/v3 时，复用窗口 1 的 `read_evidence_history(path, handoff=...)` 展开 1.json 到当前版本，每版 path/sha256/evidence_version 均进入 evidence_records 和版本台账。v1 可直接使用非数字文件名；后续版本必须使用标准数字文件名。接收重放摘要包含旧版文件指纹，旧版改变、缺失或版本冲突时，不允许只转交最新版绕过历史保护。证据版本台账写入整段成功或整段撤回；原件可保持已接收并明确记录证据限制。

证据中的 request_records 原样保留引用，不由接收模块认定请求用途或授权重发。第三状态仍须区分 Nimble 分类请求与附件识别请求，并检查全链历史。

## 集成归属

只合入 receipts.py、receipt_history.py、intake_handoff.py、receipt_cli.py 以及 intake.py 的新增薄入口。候选内 records.py/__init__.py 是离线依赖副本，**不要覆盖窗口 3 的 records.py**。主工程 backend/workflow/flows/attachments 均由窗口 3 接入。
