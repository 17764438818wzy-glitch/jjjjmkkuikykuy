# Prefect 分阶段流水线改造设计

日期：2026-10-29（America/Los_Angeles）。状态：供用户审阅的设计提案；尚未实施或部署。

## 1. 目标与已经确认的原因

目标：用户一次提交资料，Prefect 按论文和阶段连续调度；RAG/NAS 等待不阻塞其他论文的 LLM；失败可定位、可恢复；完成必须有入库和归档证据。

当前本机 SDK 为 Prefect 3.9.0。`manage.py:36,66` 同时把部署和 Runner 限制为 1 个整批运行；`unified_flows.py:120-137` 的论文名额覆盖整条五步链，批次等待所有论文的下游结束。`flows.py` 依赖进程内 `_batches`、局部 semaphore 和统一阶段包装；业务任务设置 `retries=0, persist_result=False`。业务文件确有持久记录，不能误称现在完全没有保存结果，但这些记录没有构成独立任务的可靠交接。

2026-10-29 14:59 的诊断快照：310 组中的 227 组正文画像已通过，45 组上游失败/中断，28 组取消/重启后结果未知，其余 10 组涉及校验、身份、准备或材料问题。该数字是历史基线，实施前重新核对，不用它冒充实时状态。

原始请求日志复核：24 次 502 在 10:43:51—10:44:33 启动，约 122—129 秒失败；20 次长响应在 18—29 分钟后收到上游 `Node transport: ECONNRESET`；另有 1 次 429。共同超时/连接问题是待路由端证据确认的假设，不写成已查明的网关根因。

## 2. 方案选择

| 方案 | 评价 |
|---|---|
| 只提高整批并发、保留整篇占位 | 可让多个批次重叠，但保留长持锁、内存上下文和恢复断点；不推荐作为正式修复 |
| 单个长 Flow 内把所有步骤改成 submit/map | 能表达依赖，但共享执行池和父进程仍须处理下游等待、崩溃恢复；不作为这次最终结构 |
| 分阶段 Prefect 后台任务，独立 Task Worker | 本设计推荐；隔离 LLM、RAG、NAS 执行容量，持久交接，实现一次提交的完整业务流程 |

本设计采用第三种作为待审阅方案。正确性和持续吞吐优先；允许重写调度入口、阶段包装、恢复路径。保留历史结果与身份属于数据完整性要求，不是对旧调度实现的保留要求。

## 3. 固定边界

- Prefect 是唯一常规任务队列和并发控制来源；不新建 Redis/Celery 调度器，不再用 `_batches` 或整批 semaphore 决定可执行论文。
- 版本固定 Prefect 3.9.0，先验证该版本的后台任务、结果存储和故障恢复；本次不顺带升级 Prefect。
- 第一版所有业务 Task Worker 运行在这台 Windows 主机，共用本地业务路径；现有 LAN Prefect Server 负责状态与调度，RAG 服务端继续通过 API 使用。暂不把 Windows 路径任务搬到 Linux。
- 正文 HTTP 全局上限 100，附件 HTTP 20，模型总 HTTP 120；本地转换 4、封包 2、RAG 交付 20、NAS 2。所有批次、正常请求和恢复请求共享相同额度。
- 初始模型启动速率为 1 次/秒、突发容量 1，作为待实测的保守默认值；它限制新建请求频率，不把同时在途请求限制成 1。路由验证后调整速率，不按显存占用猜上游容量。
- Worker 任务容量与 HTTP 额度分开：正文 128、附件 32、模型恢复 32、本地准备 4、封包 2、RAG 40、NAS 4、控制/核对 8。128 是正文任务容量，实际模型 HTTP 仍不超过 100。正常模型任务与恢复任务使用不同 task_key、不同 Worker；等待重试不能占满正常任务 Worker。
- Task Worker 默认 limit=10，必须显式配置。3.9.0 任务重试等待仍可能占用 Worker 任务容量；不能宣称 AwaitingRetry 自动释放 Worker。HTTP 额度必须在每次实际请求结束时释放。
- 业务记录按实际任务身份校验；Prefect 参数/结果持久化仅保存轻量引用，不传整篇文本、图片或密钥，不用框架缓存跳过业务证据核验。
- 旧生产文件不热覆盖；候选版本隔离建设，切换时有明确运行代号和执行权隔离。
- 只处理冻结范围内的资料。早上已收尾的 100 组作为完成记录核对；当前 310 组建立逐项迁移清单；不扫描扩入其他历史论文。
- 原桌面资料不改动。已授权的 inbox 副本清理仍须整篇证据齐全；不得扩展删除范围或另改保留策略。
- 下游显示与新增交付文件遵守正文“论文题目.扩展名”、附件“论文题目_附件自身名.扩展名”；原名和来源映射保留，身份不依赖显示名，不原地改写既有接收回执。

## 4. 工作流与完成语义

```mermaid
flowchart LR
    A[一次提交并冻结范围] --> B[分流与逐项接收]
    B --> C[正文准备]
    C --> D[正文 LLM]
    D --> E[画像校验并持久保存]
    E --> F[封包]
    F --> G[正文 RAG 交付与核验]
    B --> H[附件识别与说明]
    H --> I[附件 RAG 交付与核验]
    G --> I
    G --> J[整篇收录核对]
    I --> J
    J --> K[NAS 复制与读回]
    K --> L[按已授权规则收尾并记录完成]
```

正文与附件识别独立；已确认正文不因附件待核对而停止模型处理。附件入库等待本篇父正文对象，其他论文不等待它。无附件必须有明确空清单，可跳过附件分支。

LLM 结果持久保存后，上游步骤结束，封包和 RAG 由各自 Worker 继续。RAG 第一期允许一个交付任务等待其远端核验，但只占 RAG 执行容量，不占 LLM、整篇或批次执行名额；服务端解析、嵌入优化单独验收。

长文已有分段请求按 part_id 保存与恢复；只补可确认失败的部分。分段间有模型上下文依赖时保留依赖，不为追求数字强行并行。整体画像须分段齐全并通过汇总校验。

批次提交 Flow 的 Completed 仅表示“提交登记完成”；业务状态用 `paperflow-batch-progress/2` 表达 submitted/running/draining/paused/needs_attention/partial/completed/cancelled。最终 completed 要求清单内每篇满足整篇完成规则。失败不会冒充完成，也不会让其他独立论文停下。

## 5. 持久交接与重复执行

新目录：`runtime/data/pipeline-v2/<batch_id>/` 保存冻结清单、控制记录、迁移映射和进度快照；逐阶段操作记录使用全局稳定 operation_key 存入 `runtime/data/pipeline-operations/<operation_key>/`。

`operation_key` 由稳定论文身份、材料/附件 ID、内容哈希、阶段、分段 ID、输入结果哈希和该阶段处理契约版本计算。batch_id、显示文件名、Worker PID、尝试次数不进入身份。更换 Prefect 调度代码不自动失效已验证的模型结果。

交接顺序：核验并保存结果 → 保存下游交接意图 → 向 Prefect `.apply_async()` 投递 → 保存 task_run_id。任务只能接收论文身份、回执路径/哈希、operation_key、批次控制代号、dispatch_seq 和结果引用，禁止依赖全局 Backend 实例。

进程可能在“Prefect 接受投递但本地尚未保存编号”之间退出。补偿核对先按 operation_key 标签查询 Prefect，再确认交接；查询结果不明时不立即重投。即使重复 Task Run 已产生，业务操作锁及原请求/交付记录必须阻止重复模型调用、重复远端文档。

本机 3.9.0 后台任务的交付队列使用进程内 TaskQueue，查到数据库中的 Scheduled 记录不能证明 Server 重启后还能被消费。远端 Server 版本与这一行为必须在隔离验收中核对。恢复规则：同 task_key 存在版本匹配、存活且有空位的 Worker，Scheduled 超过 120 秒仍未领取，且业务未发送、没有有效拥有者时，核对 Flow 可在操作锁下递增 dispatch_seq 并重新投递，保存新旧 Task Run 对应关系。旧投递之后即使被领取，也因 dispatch_seq 过期在外部调用前退出。Pending/Running 仅在旧 Worker 和它拥有的子进程已确认死亡后按业务记录处理；已发送的先进入 unknown，禁止按“排队丢失”重投。没有空闲 Worker 的正常排队不触发重排。

跨进程锁细分为：短期接收身份写锁、具体阶段 operation_key 操作锁、原生模型/发布对象操作锁。移除覆盖整篇五步的长锁，但不删除模型和外部写入所需的互斥。

Prefect 每 15 秒执行一个核对 Flow：仅检查当前明确登记批次的交接遗漏、失联任务和远端未知结果；不计算常规资源额度、不另建运行队列。进程消失后的已发送请求转为“待核对”，不能当作未发送。

所有新 Worker 必须能够访问同一份任务参数/结果存储。部署前用独立进程验证，不用“能注册部署”替代这一验收。

## 6. LLM 失败治理

### 6.1 路由诊断与记录

同一 request_id 贯穿论文操作、Prefect task_run_id、API 路由、WorkBuddy 适配器。记录路由/通道的非敏感 ID、发送时间、首响应/首 token、最后响应、HTTP 状态、远端错误码、Retry-After、请求字节和图片数；不记录密钥，不在普通日志输出全文。

针对 24 次约两分钟的 502，对齐 10:43—10:47 本地时间（UTC-07:00）的网关和适配器日志，确认每一跳的连接、首包、读取及总超时。针对 20 次 ECONNRESET，查同请求的远端关闭、出口代理、Node 进程退出或资源错误。没有对应日志只能记录假设和观测缺口，不能写“已修复网关”。

LLM 总时限先保持当前 3600 秒；各跳超时依据日志与成功请求分位数确定，不先整体缩短造成新截断，也不只把所有超时统一调长。

### 6.2 重试与未知结果

| 结果 | 策略 |
|---|---|
| 确认没有发出 HTTP | 修复本地准备/连接问题后正常投递，不扣模型发送次数 |
| 确认可重试的 429 或服务拒绝 | 最多 2 次追加模型请求；等待基准 30、120 秒，加 0—25% 随机错峰，并尊重更长 Retry-After |
| 502/503/504，但是否已被上游执行不明 | 进入核对；不能仅凭 HTTP 码自动判定可安全重发 |
| 流已开始后 ECONNRESET、读超时、进程丢失 | 保留部分响应、原请求身份和用量未知；先查原结果，不直接重发 |
| 完整回答已经保存，仅格式/校验失败 | 先离线恢复/校验；无法修复的标需处理，不自动再调用模型 |
| 身份、源文件、模板证据不匹配 | 停本项并给明确原因，不阻塞其他论文 |

追加次数使用持久发送预算，先预留再发送；进程重启、任务重建不能重置预算。现有 retry-intent/revision 消耗全部计入。此前仅三篇各一次的重发授权不扩展成所有未知请求的重发授权。

正常模型任务不在原 Worker 内循环重试；记录明确失败后向独立 `model_recovery` task_key 投递。恢复 Worker 等到 not_before 再申请 HTTP 额度，第一次追加请求失败后由 Prefect `retry_condition_fn` 和最多一次原生重试安排第二次追加请求。长 Retry-After 只占恢复 Worker；若超过 600 秒，转 needs_attention 并记录下次允许时间，不提前重发。业务适配器必须允许被批准的下一次尝试，不能只改 retries、却继续被旧的“一次性恢复”门禁挡住。分段按 part_id 记账，同时整篇最多 2 次追加 HTTP；已有消耗扣减，不无限按分段叠加预算。

`model_recovery` 是执行任务类型，不是新的业务阶段：恢复信封仍指向原 profile/attachment 的 operation_key，dispatch_kind=recovery、dispatch_seq 更新，尝试记录另存。恢复成功完成原业务阶段并派发其下游；不能创建一个与原失败阶段无关的“恢复成功”状态。

未知结果：每 30 秒核对一次，最长 10 分钟；提供方不支持查询时立即说明该能力缺失，转 needs_attention；期限后仍未知也转 needs_attention，停止自动核对。该状态不占 HTTP 名额，不显示永久 Running；新证据到来后可再次核对，重发需要与该论文对应的明确授权。

单路由 60 秒窗口至少 10 个终止请求且可用性错误率 >=30% 时，建议开启 60 秒冷却，仅停止该路由新派发；保留在途请求和其他步骤。冷却只用就绪业务请求试探恢复，不额外生成计费探测请求。策略属于适配器业务规则，由 Prefect 控制 Flow 更新路由状态；不另建调度器。

## 7. 停止、部署和迁移

用户只有一个提交入口及全局/批次控制。持久控制记录含 desired_state、generation、scope_id。每次新外部操作前检查控制；进程启动不能自己把 paused 改成 running。

信封同时携带 global、batch、runtime 三种控制代号。控制代号变化拦截新的外部操作，但允许已开始的请求把已获得的结果保存成证据，避免暂停时丢弃成功回答。

正常暂停：停止新领取，在途操作把结果保存到中间态。紧急停止：停止本地等待并关闭可关闭的传输，已经发送到上游且不能确认结束的请求记为 unknown；不声称远端随本机进程一起消失。切换不要求等待所有 RAG 入库，只要求当前阶段的已知结果/未知结果归档、旧进程失去新派发权。

执行模型明确为：LLM 请求使用可取消的异步 HTTP 客户端，画像输入构造、HTTP 流收取、离线解析分开，不能把旧同步调用包在线程中就宣称可取消。RAG/NAS 保留同步业务协议时，放进由对应异步任务监督的独立子进程；父任务记录 PID 和创建时间、阶段身份，取消时先请求退出，10 秒未响应则终止经身份核对的子进程，再保存未知结果。所有后台子进程隐藏窗口。阻塞网络故障注入要求本地传输/子进程在 15 秒内退出；外部结果未知单独显示。

Prefect 并发租约拟配置 60 秒并自动续租（SDK 默认 300 秒）；先验证 Server 支持及续租故障行为。硬杀 Worker 的名额回收按“租约到期 + 服务端清理周期”实测，目标 <=90 秒；达不到就保留实测限制，不宣称即时释放。禁止把全局 active_slots 直接清零。客户端 HTTP 在途和远端结果未确认分别统计，本地名额释放不等于远端模型已经停止。

迁移输入从明确的批次回执构建，不从整个历史目录发现任务。重新核对后：已完成论文不执行；画像已通过的直接进入未完成下游；已有 RAG 文档按原 ID 核验/续处理；未发送的进入正常 LLM 队列；明确失败和未知分别走上述策略。

回滚只撤回新执行版本与入口绑定，保留所有新旧业务结果和请求记录。v2 写过的操作在旧执行器验证兼容前保持冻结；不把旧程序直接指向 v2 处理过的数据重跑。无 Git 的当前目录使用候选目录、逐文件 SHA256 和部署导出形成回滚清单，不擅自初始化仓库。

## 8. 前端与指标

前端继续一次提交；新增版本化提交/控制/状态契约和 Prefect artifact，不要求前端理解 Worker 调度。字段至少包括 paper_id、论文题目、来源映射、当前阶段、LLM/附件/RAG/NAS 独立状态、失败原因、下一次恢复时间、请求尝试数、Prefect 运行链接和最后更新时间。

状态快照含各阶段 ready/running/retry_wait/unknown/failed/verified 数量，以及真实 HTTP 在途数、配置额度、Worker 正在执行数、最近 5/15/60 分钟完成量、首响应与总耗时 P50/P90、错误分类及路由。旧的静态名单保留时间标记；快照超过 30 秒未更新显示状态过期，不显示伪实时数据。

“LLM 已完成”只按画像校验完成计数；一次模型响应、一个分段或一个 RAG 专业目标完成不算整篇完成。

## 9. 验收与实施顺序

先隔离验证 Prefect 后台任务，再做独立任务/持久交接，再做请求预算与恢复，再做状态接口和旧记录迁移，最后切换真实范围。网关日志诊断可以与代码改造并行推进；网关问题未闭环时，只能宣布调度测试通过。

必须通过：

1. 生成 400 篇模拟任务，正文请求保持 180 秒、RAG 阻塞 600 秒；模型启动速率 1 次/秒，足以在第一个请求结束前达到 100 在途；第一批未收录时第二批正文仍启动，有足够 eligible 请求时持续补位，且始终不超过 100。
2. 预热后 eligible 请求 >=100、路由健康且启动速率未成为瓶颈的采样中，正文 >=95 并发的样本占比 >=95%；空出一个名额后有 ready 时 95% 补位 <=5 秒。末尾不足 100 或本地准备不足单独报告，不伪造满载率。
3. 模型恢复 Worker 的全部 32 个容量都处于 retry_wait 时，正常 Worker 仍可领取健康路由的 ready 输入；等待重试不占 HTTP 槽。
4. 故障注入覆盖：保存后未投递、投递后未存编号、Prefect Server 重启丢失后台交付队列、Pending 拥有者消失、发送后崩溃、响应完整但未校验、RAG 接受但本地未收据、NAS 已复制未记账、挂死传输时紧急停止、全局暂停与多批次同时发生。
5. 反复提交与重启：已验证模型输出产生 0 次新模型请求，已有文档产生 0 个重复文档；未知结果不会自动重发。
6. 真实测试先 5 篇端到端，再按 20/50/100 并发档推进，每档至少观察一个完整模型响应周期；实际 eligible 不足时不人为重跑已完成论文凑 100。真实每小时成功画像量、整篇收录量和错误率分别报告。
7. 完成必须逐专业目标读回、内容/身份核验、NAS 文件哈希核验；前端完成统计与业务回执一致。
