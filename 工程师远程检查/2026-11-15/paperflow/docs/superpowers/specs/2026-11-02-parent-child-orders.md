## 必须实现的业务行为

1. 新建任务前检查本次配置的所有必要依赖；检查通过才创建任务。用户最新定案为“自检出现问题，然后自动修复”：明确识别到依赖未启动且已有对应启动入口时，自动启动并复检，复检通过才放行。原因不明确或恢复失败时报告具体原因并阻止创建。检查不调用真实模型，依赖恢复不等于自动开始业务或重试未知请求。
2. 大工单是原生 Prefect 父流程；分类通过、交付完整且登记成功的每个论文文件夹对应一个原生子流程。正文和附件属于同一小工单。一篇就绪就允许进入后续阶段，不等整批。
3. 同一个小工单贯穿前处理、LLM、后处理、RAG、NAS、本机清理。大工单只有在其全部应处理小工单完成全链路后才完成。
4. 开始、暂停按所选大工单控制全部子工单。用户后续确定以最后准入为界：已获准单次请求允许发出并收尾保存，不增加额外同步；未获准的新请求不能发送。新子工单登记、下阶段、每次上传、归档或删除各自重新准入，不能放行整个已领取阶段。恢复复用已保存成功结果。
5. 多个大工单独立控制，共享现有配置的全局资源上限。服务或电脑重启后保持停止，等待页面手动开始。
6. 单篇/任一附件失败，停止该小工单在失败处，保留其他已成功结果；其他论文继续。用户手动选中失败小工单重试，不能重做已成功部分。未知结果不等同失败，不自动重发。
7. LLM 成功以完整响应已保存为准，不能等待后处理结束才显示成功。后处理是加工步骤，区分等待、执行、完成和程序失败；不能将程序错误表述为论文内容不合格。保留必要的输入和产物格式检查，不增设质量审核关卡。
8. 每篇论文最终产生一份基于全文的专业排名，无论是否分段。分段只用于处理材料，不能以某段局部排序决定整篇入库；全文结果必须覆盖全部正文材料或完整分段处理结果。按最终全文结果识别出几个有效专业就入几个，最多三个；超过三个按关联度取最高前三。不能补齐三个、按编码排序或临时建测试库。使用现有正式专业库。零个有效专业不能当作已入库。
9. 全部选定专业的 RAG 入库均成功才能清理；部分成功时只补失败目标。正文和所需附件不允许通过“部分发布”绕开失败。
10. NAS 保存一份原文和原始附件，与入库专业数量无关。以所需文件实际保存成功为条件，不增加指纹、哈希或下载回读流程。
11. 每篇全目标 RAG 成功且 NAS 文件保存成功后，立即删除该篇本机原始文件、任务副本及中间产物。原始来源文件也在用户确认的删除范围内。未归档的异常杂物保留，不直接递归删除整个来源目录，不删除共享数据库或程序。
12. 清理完成后，必要工单状态、结果凭据和防重复发送记录留在服务器/Prefect，不留该篇本机记录。未确认服务器持久化不能当作已清理完成。
13. 页面统计只针对所选大工单，未知/不完整信息不能填假零。正文和附件同时运行仍算一篇。暂停显示实际阶段及状态。
14. 历史工单和测试材料保持原状；新架构应用于新任务，不在本轮迁移、删除或重试历史任务。

## 工程边界

- 防过度防御：几乎不会发生的边界/并发问题，先说明概率并经用户确认再增加处理，严禁为了“理论上更稳”膨胀代码。
- 入口单次校验：外部数据只在边界校验一次，内部靠明确类型流转，禁止层层重复判断。
- 拒绝提前抽象：单次使用逻辑就近内联，不随意拆分无意义 helper。
- 控制复杂度：非必要不用 try/catch，能用一个函数清楚完成的逻辑不要硬拆。
- 通用规则：所有修改解决一类业务问题，不针对当前测试论文、文件名、论文ID或特定内容写特例，也不为通过样本放宽判断；应失败或待核对的输入保持正确结果。不得把通用性理解为提前造框架或扩展未授权范围。
- 确定且在职责范围内的修改可推进；业务含义、范围或必要技术取舍不确定时，先交协调窗口向用户说明，不能按猜测修改。
- 新后端根目录：`candidates/parent-child-v3-20261102/`。用户已授权此版本作为8796验收入口运行；其他旧服务和历史任务保持原状。
- 工单窗口独占 `paperflow_v3/control/`、`tests/control/`；它负责依据真实调用确定最小公共接口及 API。需要公共文件时由它单独维护，不要求预建协议框架。
- 调度窗口只维护本文件、总计划、窗口状态和交接清单；不改业务代码。
- 论文处理窗口独占 `paperflow_v3/stages/`、`tests/stages/`、`STAGES_HANDOFF.md`。
- 入库清理窗口独占 `paperflow_v3/delivery/`、`tests/delivery/`、`DELIVERY_HANDOFF.md`。
- 前端窗口独占既有 `candidates/prefect-folder-frontend-20261101/`。主窗口不改前端文件。
- 如需修改既有处理脚本，先把必需的少数文件放到各自负责目录作候选覆盖，记录原路径和改动点；不要改其他窗口文件。
- 单元及集成检查只用合成数据、临时目录、隔离服务。禁止真实论文、线上调度、真实模型、RAG 写入、NAS 写入和来源删除。

## 后端接口

不要在核查真实调用前预建通用运行时或另造一套论文资料格式。工单窗口先确认现有脚本如何接收单篇输入、返回结果、准入和保存凭据，随后在自己的 CONTROL_HANDOFF.md 发布最小公共接口。论文和入库窗口先做复用核查及确定的本模块修改；跨模块接线等输入输出确认后再改。

最小接线必须覆盖：一个原生子工单的身份、明确资料清单、各阶段结果、开始/暂停准入、服务器持久化凭据以及现有配置的全局资源。获取资源后实际发送前也要核对是否仍允许运行。已发请求暂停后允许收尾保存；未知请求保留原请求身份，不能换键重发。合成测试替身不能冒充生产服务器存储。

## 页面接口约定

下列为协调窗口整理的接口提案，不表示已有在线地址或已定案。工单窗口根据现有 API 核查并给出最终接口，前端窗口据此接线，不能把提案当成在线接口。接口字段/路径属于工程选择；若改变业务语义，先向用户确认。前端配置未提供新 API 地址时保持不可调用，不回退旧控制。

- `GET /api/v1/prefect/folder-tickets?task_id=...`：`task_id` 必填，只返回该大工单；保留既有《后端接口需求.md》的 `as_of`、`complete`、`folders` 及每篇字段。`complete` 表示本次快照完整，不表示大工单完成。新增顶层 `task_id`、`desired_state`（running/paused）、`task_state`。`failed_stage` 增加 `cleanup`；清理失败仍停留在原小工单。
- `GET /api/v1/prefect/tasks`：返回 `{as_of, complete, tasks:[{task_id, task_name, parent_flow_run_id, desired_state, task_state}]}`，供选择任务。
- `POST /api/v1/prefect/preflight`：依赖检查，并对已识别且有现成启动入口的未启动依赖自动恢复、复检，返回 `{ready, checks:[{name, ready, detail}], checked_at}`。创建任务必须由后端重新执行检查，不能相信浏览器传来的 ready；恢复过程不发推理、不处理论文。
- `POST /api/v1/prefect/tasks`：请求 `{task_name, source_paths:[...]}`；只接受该次明确选择的本机资料路径。成功返回新大工单字段；依赖失败返回 409 和检查结果。上传机制与路径选择沿用前端现有可用能力，不能将本机路径误传成服务器路径。
- `POST /api/v1/prefect/tasks/{task_id}/start` 与 `/pause`：空对象请求，返回当前大工单字段；未知调用结果保持未知，不自动重发。
- `POST /api/v1/prefect/tasks/{task_id}/folders/{folder_id}/retry`：空对象请求，手动重试失败点；成功阶段保留，未知请求拒绝自动重发。
- 历史任务删除及文件上传接口不在并行窗口自行重写范围内；工单窗口核对原先确认的删除语义，存在缺失则交协调窗口询问用户。没有新接口时前端不得回退旧接口。
