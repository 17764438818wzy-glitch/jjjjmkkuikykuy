# Prefect 连接池耗尽：官方处理方式与本项目建议

核查日期：2026-11-02。本文用于沟通方案，未改配置、启动任务、重试业务或删除数据。以 Prefect 3.9.0 官方源码和同版文档为主；官网页面无法抓取时，直接核对官方仓库里的原文。

## 结论

**解决方向是减少无效报备、缩短每次查询，再根据数据库承载能力增加连接容量。15 不是 Prefect 的任务并行上限，也没有依据通过删除论文、RAG 内容解决这次故障。**

“15 个窗口”准确地说，是本次报错的一个 SQLAlchemy 连接池：5 个基本连接，加最多 10 个临时连接。API 多进程、多个实例或后台服务可能各有连接池，不能把 15 当作整个部署的永久总数。[3.9.0 设置源码](https://github.com/PrefectHQ/prefect/blob/3.9.0/src/prefect/settings/models/server/database.py#L89-L127)、[数据库引擎源码](https://github.com/PrefectHQ/prefect/blob/3.9.0/src/prefect/server/database/configurations.py#L205-L355)

## 官方怎么处理

1. **先查为什么连接占满。** Prefect 底层 SQLAlchemy 的官方错误指南列出：同时请求过多、连接未归还、事务过长、锁等待等。对应处理是修正占用原因，并合理调整池容量或请求并发；不建议用无限连接掩盖问题。延长等待时间只让请求多等一会儿，不增加办理速度。[SQLAlchemy 官方错误说明](https://docs.sqlalchemy.org/en/20/errors.html#queuepool-limit-of-size-x-overflow-y-reached-connection-timed-out-timeout-z)
2. **连接池可以配置。** 3.9.0 支持以下服务端设置；本项目当前恰好使用默认值。[设置源码](https://github.com/PrefectHQ/prefect/blob/3.9.0/src/prefect/settings/models/server/database.py#L89-L127)

   | 环境变量 | 当前值 | 含义 |
   |---|---:|---|
   | `PREFECT_SERVER_DATABASE_SQLALCHEMY_POOL_SIZE` | 5 | 基本连接池容量 |
   | `PREFECT_SERVER_DATABASE_SQLALCHEMY_MAX_OVERFLOW` | 10 | 繁忙时允许增加的连接数 |
   | `PREFECT_SERVER_DATABASE_SQLALCHEMY_POOL_TIMEOUT` | 30 | 等待可用连接的秒数 |

3. **先看指标，再扩容。** Prefect 官方要求关注数据库连接耗尽、接口耗时、后台处理积压；规模需要时，可以把 API 与后台服务分开，再配置多 API 实例、Redis 和负载均衡。不是发生一次超时就必须搭整套集群。[同版自托管扩容文档](https://github.com/PrefectHQ/prefect/blob/3.9.0/docs/v3/advanced/self-hosted.mdx)
4. **业务通道满，官方会等待。** 3.9.0 的并发槽服务在收到 HTTP 423 后按 `Retry-After` 等待；同一进程、同一组限额的申请由一个服务顺序办理。这里顺序办理的是“申请”，不代表论文串行处理。数据库异常产生的 HTTP 500 不属于正常的“通道满”。[并发槽源码](https://github.com/PrefectHQ/prefect/blob/3.9.0/src/prefect/concurrency/services.py#L42-L181)

## 本项目现有证据与建议

以下运行证据来自调度窗口本次只读核查：服务端和客户端均为 3.9.0，PostgreSQL 18.6，数据库连接上限 100；API 容器 2 CPU / 3 GiB，数据库 1 CPU / 768 MiB。11 月 2 日 09:33:27（洛杉矶时间）发生大量池等待超时，随后大工单失败。176 个小工单中，20 完成、155 失败并记录 API 500、1 崩溃。当前 API 恢复健康，不代表故障已经根治。

本地代码已确认两个额外负担：暂停或等待开始时，每个等待循环每 0.2 秒读取两个 Prefect 变量；打开任务列表还会逐项汇总子工单回执。本次同一大工单原生元信息查询约 0.21 秒，而项目列表接口约 64.17 秒。**这些证明存在多余查询和重查询，但不足以证明它们是运行中本次耗尽的唯一原因。**

建议按这个顺序处理，具体改动仍待用户确认：

1. 优先让“打开任务”只读取列表所需信息，进入具体任务后再读取详情；缩减暂停等待中的重复状态查询，保留用户约定的最后准入检查。这属于项目修正，不是 Prefect 官方要求重写调度。
2. 针对故障时段核对 API 耗时、Postgres 活动事务/锁等待，以及 CPU、内存和磁盘压力。`pg_stat_activity` 可以区分正在执行、空闲事务、等待事件；当前空闲快照不能还原昨晚原因。[PostgreSQL 18 监测说明](https://www.postgresql.org/docs/18/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)
3. 若数据库有余量，再提高 Prefect 池容量。必须把 API 与后台服务的各个池合计，并留出管理连接；不能直接把单池开到 100。数据库目前只有 768 MiB，不能仅凭连接上限认定可承受更多并行查询。Postgres 官方也说明，提高 `max_connections` 会增加包括共享内存在内的资源分配。[PostgreSQL 连接设置](https://www.postgresql.org/docs/18/runtime-config-connection.html#GUC-MAX-CONNECTIONS)
4. 保持前处理 10、后处理 10、RAG 20、NAS 2 的业务目标；如仍有服务端处理瓶颈，再按官方文档分离和扩容。验收同时看阶段吞吐、接口耗时和连接错误，不能只看任务数量或某篇论文是否通过。

## 不宜套用的“修复”

- 官方“用全局并发限制保护数据库”的示例控制的是业务代码的 `db.execute`。申请 Prefect 全局并发槽本身也需要调用 Prefect API，因此不能直接给每次 Prefect API 请求再套一层 Prefect 限流，声称即可保护它自己的数据库；那会增加同一服务的请求。[官方示例](https://github.com/PrefectHQ/prefect/blob/3.9.0/docs/v3/how-to-guides/workflows/global-concurrency-limits.mdx#L271-L294)、[申请槽源码](https://github.com/PrefectHQ/prefect/blob/3.9.0/src/prefect/concurrency/services.py#L54-L80)
- 已查 3.9.0、3.9.1 发布说明及相关官方仓库 issue，**未找到能把本次 5+10 连接池耗尽直接归因于特定版本缺陷的证据**，不能承诺升级就解决。3.9.1 的确已有其他修复，但需逐项匹配本项目故障。[3.9.0 发布说明](https://github.com/PrefectHQ/prefect/releases/tag/3.9.0)、[3.9.1 发布说明](https://github.com/PrefectHQ/prefect/releases/tag/3.9.1)
- 仓库 issue #22912 报告的是维护任务专用池 `pool_size=1, max_overflow=0`，不是这里的 5+10；它也只是缺陷报告，不能作为本次根因。[维护池 issue](https://github.com/PrefectHQ/prefect/issues/22912)

尚缺故障时完整的查询耗时、事务/锁等待、连接数量和资源曲线。因此现在可以确定“服务端连接池耗尽”，可以确定项目有额外查询负担；不能确定哪一类请求占用连接最久，也不能给出已验证的最佳池大小。
