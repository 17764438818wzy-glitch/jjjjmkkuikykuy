# Linux 服务器迁移：新任务交接说明

这是已验证 Windows 工作台的迁移任务，不是重写预处理规则。用户希望在 Linux 服务器长期运行，并强调不能破坏原来正确的功能。先调查环境、形成具体迁移方案及回归清单，再分阶段实施和验收。

## 现有项目与保护要求

- 主项目：`E:/uv/ragflow_upstream`。当前工作区有大量未提交及未跟踪的有效改动，不能 reset、clean、覆盖或仅从 HEAD 创建旧代码副本。创建隔离环境时必须包含当前完整工作成果。
- 存在主项目外的 `E:/uv/src` 依赖，尤其 `engine.py` 的旧模块导入；`LEGACY_ROOT` 还指向 `E:/dity/脱敏分类脚本/脱敏分类脚本/cleaning-pipeline`。先追踪这三处的实际依赖，再整理为可部署的包。不要直接复制整个磁盘资料目录。
- 当前 `requirements.txt` 是 Windows 多仓库运行环境快照，含 Windows 专用包和可能无关的依赖。不能直接原样用于 Linux 安装；按实际导入链整理核心、桌面、服务器和测试依赖，并保留版本验证记录。
- Windows 入口 `launch.pyw` / `app.py`，Tkinter 桌面界面；Python 核心处理已相对独立，可复用。
- 读取 `docs/script-task-page.md`、`docs/audit-103-fixes.md`、`docs/superpowers/plans/2026-09-20-ai-resume.md`、`docs/superpowers/plans/2026-09-20-rag-results.md`。以当前代码和当前测试为最终基线。
- 最近一轮修复验证为 881 通过、1 个既有配置断言失败。失败 `test_saved_runtime_config_enables_configured_fallback_channel` 要求真实用户配置启用备用模型，但用户实际关闭它；不要为让测试通过改变用户偏好。迁移开始时重新记录基线。
- 测试应枚举项目根目录 `test_*.py`，避免递归收集备份副本；现有 Tk 测试和 Windows DPAPI 测试需与可在 Linux 运行的核心测试区分，不能简单删除失败测试。

## 推荐运行形态（待环境确认后落地）

浏览器工作台 → Python Web 服务 → 持久化后台处理任务 → RAGFlow。

保留成熟的脚本和 AI 核心，替换桌面操作入口。可采用 FastAPI 和轻量网页，使用 Docker Compose 管理服务与持久化目录；无需为了迁移引入复杂前端框架或多机集群。长任务必须独立于浏览器请求运行，关闭网页、刷新页面或 Web 进程重启不应丢失任务。Web 请求进程不能直接共享一个未加跨进程保护的 JSON Store 进行并发修改；首版可选择明确的单写入任务服务，再根据规模选任务状态存储。

## 保留的产品行为

1. 选择与处理：开始前选好文件、模型、并发及论文/图片目标知识库；本批为同一专业，不新增自动路由复杂度。展示脚本进展及通过/未通过列表，筛选、全选、取消全选、反选保持一致。
2. AI 处理结果：查看原因、调整 AI 设置、重新跑选中未通过项。必须复用完整脚本检查点，不能偷偷重新解析、转换或提取图表；通过且输入未变的合格模型结果按现有缓存规则复用。
3. RAGFlow 处理结果：上传与远端处理状态分开筛选；目标库只读；重试只作用于选中且需要恢复的项目，不重复启动已完成、排队或正在处理的文档。保留部分失败、待确认、查询异常等区别。
4. 保留批次记录、处理详情、停止、并发限制、费用记录与原文/结果查看。网络断开、任务停止及服务重启必须有可追踪状态。
5. 用户期望预处理完成的论文及时上传，不要求“一次只处理一篇”。迁移时先核实现有自动交接触发时机，历史实现曾在批次结束触发；不要把尚未实现的流式上传当成现有能力，也不要与系统迁移混在一起未经说明改变任务语义。

## 必须核查的迁移点

- Windows 路径、盘符、大小写、文件名编码和本机文件选择：网页上传与服务器导入目录需要明确区分，网页不能直接使用用户电脑的 C:/ 路径。
- `auto_config.py` 使用 Windows DPAPI；`.dpapi` 文件不能直接作为 Linux 可读密钥。Linux 改为受控环境变量/挂载密钥文件等方式，网页只返回“已配置”或掩码，不返回真实密钥，不写入日志或仓库。不要先行读取或打印现有真实密钥。
- `engine.py`、`auto_evidence.py`、`evidence_tasks.py`、`evidence_render.py` 中的 LibreOffice 路径，以及 `os.startfile`、Windows 互斥锁、`ctypes.windll`，需要平台适配。
- Linux LibreOffice、中文/西文字体、PDF 依赖与版本需实际验证。WMF/EMF 已修复为独立 LibreOffice profile 渲染；不能退回会造成公式重叠的旧 Pillow WMF 路径。并发任务必须隔离转换 profile 和临时文件。
- 文件锁、原子保存、任务所有权与崩溃恢复需适用于服务进程。端口、目录、数据卷、服务用户与权限由部署配置管理。
- RAGFlow 地址和容器网络需从服务器内部核对，不能假设 Windows 上的 localhost/内网地址在服务器上同样可用。保留已验证的上传去重、回执核对和未知状态保护。
- 历史 manifest 含绝对 Windows 路径；源文件、资产、检查点之间的路径和哈希需设计迁移策略。不能简单全文替换盘符后把旧检查点标为可恢复。
- 旧 103 条失败后续已恢复 19 条；剩余 84 条均无新版可信检查点，其中 27 条无完整脚本产物、57 条仅有旧中间资料。此次迁移不能伪造其可续跑状态。

## 开始前向用户一次性收集

- Linux 发行版、版本、CPU 架构、CPU/内存、可用磁盘。
- 是否已安装 Docker/Compose，是否已有 RAGFlow，以及实际部署方式和网络。
- 可使用的 SSH 连接方式（通过安全配置提供凭据，不在聊天粘贴密码/密钥）。
- 内网还是公网访问；域名/HTTPS/访问账号需求；计划端口和数据目录。
- 输入文件从网页上传还是已位于服务器；是否迁移历史批次、原文件和缓存，还是先只跑新批次。

缺少服务器信息时，可先完成本地依赖审计和隔离迁移方案，不臆测服务器配置。

## 验收与交付

- 先跑通 Linux 命令行核心，再接入网页三页流程，最后部署服务器；每步都有回退路径。
- 使用隔离样本验证 DOCX、PDF、旧 Office 格式、WMF/EMF、中文字体、公式、表格、脱敏、损坏/加密文件和查重附件。
- 回归串行/并发、停止后恢复、AI 续跑不重做脚本、服务重启恢复、上传去重、RAGFlow 失败重试及密钥不泄露。
- 真实模型调用先用少量经确认的样本控制费用；不要直接启动几百篇，也不要影响现有 RAGFlow 服务。
- 默认采用受限网络访问；需要公网访问时配登录与 HTTPS，并限制文件读写到配置目录。
- 交付可重复构建的依赖配置、容器/部署文件、操作说明、备份/恢复/回退步骤和验收记录。首次真实部署前展示具体服务、端口、数据卷及对现有服务的影响。
